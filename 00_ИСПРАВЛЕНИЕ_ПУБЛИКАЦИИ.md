# Исправление публикации после 29.2.5

## Подтвержденная причина

В опубликованном публичном релизе v29.2.5 обнаружен только один файл:
`WiseBase-CRM-29.2.5-mac-x64.zip.blockmap`.

В нем нет `latest.yml`, Windows-установщика и полного комплекта macOS. Поэтому запрос Windows к `/releases/download/v29.2.5/latest.yml` получает HTTP 404. Это не ошибка импорта Excel, SQL, базы CRM или вашего пароля GitHub.

Источник проверки: https://github.com/Busya228/wisebase-desktop/releases/tag/v29.2.5
API: https://api.github.com/repos/Busya228/wisebase-desktop/releases/latest
Публичный запуск Actions №11 завершился success, несмотря на неполный релиз. Предыдущий workflow не проверял комплект файлов перед открытием релиза. Почему именно остальные загрузки отсутствуют, без подробных логов публикации утверждать нельзя; отдельные сборщики больше не будут независимо заливать релиз.

## Что меняет патч

- Windows/macOS сначала собираются локально с `--publish never`, без загрузок electron-builder в релизы GitHub.
- Проверяется наличие установщика NSIS, portable, архивов macOS x64/arm64, blockmap и файлов `latest.yml` / `latest-mac.yml`.
- У файлов обновления проверяются версия, ссылки на реальные файлы, размеры и SHA-512.
- Результаты обеих платформ передаются через артефакты Actions одному заданию публикации.
- Только одно задание создает черновик и загружает весь проверенный комплект.
- Перед открытием проверяется реальный список загруженных файлов GitHub: имена, размеры, состояние uploaded и SHA-256, когда GitHub его предоставляет.
- При пропущенном/поврежденном файле процесс завершается ошибкой, релиз остается черновиком, а не становится latest.
- Номер нового релиза выбирается выше имеющихся: при текущем v29.2.5 следующий ожидается v29.2.6. Вручную менять номер не нужно.

Код приложения, импорт Excel, отчеты, клиенты, параметры Supabase и SQL этим патчем не изменяются.

## Как применить

1. Сделайте копию рабочей папки исходников.
2. Распакуйте содержимое этого архива **с заменой в ту же папку, где лежат `publish-update.bat`, `package.json`, `main.js` и `app`**. Это небольшое дополнение к исходникам 29.2.5, а не полный проект и не установщик. Не запускайте его из пустой отдельной папки.
3. Обязательно перенесите `.github/workflows/release.yml`, оба файла из `scripts`, тест из `test`. Не создавайте второй вложенный проект.
4. Запустите прежний `publish-update.bat`. Перезапуск кнопки проверки обновлений в старом приложении сам по себе не исправит уже опубликованный неполный релиз.
5. Откройте https://github.com/Busya228/wisebase-desktop/actions и проверьте новый запуск. Он должен пройти version → test → обе build → publish.
6. В новом релизе на странице Releases должны быть как минимум следующие 9 файлов (пример для версии 29.2.6):
   - `WiseBase-CRM-Setup-29.2.6.exe`
   - `WiseBase-CRM-Setup-29.2.6.exe.blockmap`
   - `WiseBase-CRM-Portable-29.2.6.exe`
   - `latest.yml`
   - `WiseBase-CRM-29.2.6-mac-x64.zip`
   - `WiseBase-CRM-29.2.6-mac-x64.zip.blockmap`
   - `WiseBase-CRM-29.2.6-mac-arm64.zip`
   - `WiseBase-CRM-29.2.6-mac-arm64.zip.blockmap`
   - `latest-mac.yml`
   Дополнительно публикуется `release-inventory.json` с контрольными суммами.
7. После успешного publish снова проверьте обновления в CRM. Если публикация остановилась, отправьте ссылку на **новый** запуск Actions или текст первой ошибки. Проверочный скрипт напишет `RELEASE BLOCKED: ...` с конкретным отсутствующим/несогласованным файлом.

Если требуется ручная установка, используйте только Setup.exe из нового полного релиза после проверки его выпуска. Сейчас в v29.2.5 такого установщика нет. Не переименовывайте случайные файлы в latest.yml и не загружайте выдуманный манифест: он должен содержать реальные размеры и хеши соответствующего установщика.

Удалять CRM, профиль приложения, клиентов или таблицы базы не нужно. Повторный запуск SQL для устранения этой ошибки не требуется. Пока новый полный релиз не опубликован, старая ошибка проверки обновлений может оставаться.

## Проверка патча

- 23 локальные проверки комплектности: отсутствие каждого из 9 файлов, устаревшая версия, неверный хеш/размер, отсутствующая архитектура, небезопасный путь, неполная удаленная загрузка, опубликованный вместо чернового статус и наблюдавшийся случай «только один blockmap».
- 4/4 профильных набора репозитория: release-files, release-version, release-consistency, desktop-main.
- Синтаксис JavaScript и структура YAML проверены.
- Формирование update metadata при `--publish never` сверено с исходником используемого app-builder-lib 26.15.3.

Это локально проверенное исправление сценария публикации. Реальные Windows/macOS-сборки и загрузка нового релиза в ваш GitHub с этой машины не выполнялись. Работа нового workflow подтверждается только его успешным запуском в вашем репозитории.
